## How to work here

- Use the Pipewright MCP tools (`pipewright mcp`) to inspect and verify: they are the live truth. Never guess names, project IDs or policies.
- Write configuration as YAML under `usecases/<name>/`. Refer to platform resources by name (`${resources.bigquery_dataset}`, `${buckets.landing}`), never by value.
- Before proposing a change, run `validate`, `doctor` and `plan` through the tools, fix what fails, then open a pull request with `pipewright review` as its description. A person approves; never merge, release, approve or deploy yourself.
- Rows of data are never sent to you. Do not ask for them, and do not paste data into the conversation.

## The rules this environment holds every use case to

- approvals.promote_model: at least `auto`.
- approvals.deploy_model: at least `manual`.
- Rows ordered in time use `data.split: { strategy: time, time_column: <cut-off> }`.
- Personal data (`data_protection.personal_data_columns`) is never a feature.
- Dates are not features; derive durations in a feature table.
- Features come from **feature tables or Feature Store feature groups** in the team's granted datasets (`data.features_from`); a use case's own table holds the entity rows and the label. A prepared table is allowed to start with, but is not the pattern. If a feature does not exist, say so in the review: the data team adds it.
